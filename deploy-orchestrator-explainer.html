01 · La idea

¿Qué es este proyecto?

Es el pequeño “control plane” de un sistema de despliegues. Un cliente le dice “quiero desplegar la versión 1.4.2 de orders”; la API registra esa intención, impone el orden correcto de estados y deja una historia durable que otros procesos pueden consultar.

Qué coordina
5 estados
queued · running · succeeded · failed · rolled_back
Qué protege
1 activo
Máximo un despliegue queued/running por servicio
Qué conserva
SQLite
Historial, idempotencia, orden y estado después de reiniciar
La frase que conviene recordar: la aplicación coordina el estado de los despliegues; no es, por sí sola, un proveedor de máquinas virtuales, un orquestador de contenedores ni un pipeline de SSH.

02 · Uso real

¿Para qué sirve en la vida real?

En una plataforma interna, un pipeline de CI/CD o un servicio de release management, varios actores pueden intentar crear o actualizar el mismo despliegue. Esta API convierte esas acciones en operaciones consistentes.

Ejemplo: servicio orders

Publicar una versión sin perder el control del estado

  1. El pipeline solicita POST /deployments con service=orders, version=1.4.2 y una clave de idempotencia.
  2. La API crea el registro como queued. La base de datos impide que exista otro queued o running para orders.
  3. Un worker o proceso de despliegue puede tomar la orden y avanzar a running.
  4. Cuando termina, registra succeeded o failed. La API conserva todos los cambios y expone cuál es la versión actual.
Ejemplo: timeout de red

Repetir una petición sin crear dos despliegues

  1. El cliente crea orders 1.4.2 con Idempotency-Key: orders-2026-08-05.
  2. El servidor crea el registro, pero la respuesta se pierde por un timeout.
  3. El cliente repite exactamente la misma petición. La API encuentra la clave durable y devuelve el mismo ID, no otro despliegue.
  4. Si la misma clave llega con otro servicio o versión, la API devuelve 409 Conflict: la clave ya está ligada a otro payload.
Ejemplo: versión defectuosa

Volver al último release exitoso

  1. orders 1.3.0 llega a succeeded y es el deployment actual.
  2. orders 1.4.0 también llega a succeeded; ahora es el más nuevo y actual.
  3. Un operador pide succeeded → rolled_back para 1.4.0.
  4. La API no borra historia: busca el deployment más nuevo que aún está succeeded, por lo que 1.3.0 vuelve a ser el actual.
Qué no hace el proyecto: no instala una imagen, no crea un contenedor, no cambia un DNS y no se conecta por SSH. Es la capa de coordinación y registro sobre la cual esos mecanismos podrían construirse.

04 · Estado

El ciclo de vida es una máquina de estados

Un deployment no puede saltar libremente entre estados. La regla existe en TypeScript para dar respuestas claras y también en SQLite para proteger la información contra escrituras que esquiven el servicio.

Regla principal: los targets válidos en general que son ilegales desde el estado actual devuelven 409. Un target que ni siquiera pertenece al conjunto permitido devuelve 400.
Estado origenTransición permitidaQué significaOtros targets
queued→ runningLa ejecución comenzó.409
running→ succeeded / failedTerminó con éxito o con error.409
succeeded→ rolled_backSe retiró el release exitoso más reciente.409
failedningunaEstado terminal.409
rolled_backningunaEstado terminal histórico.409

El estado queued no es un target de transición. Por eso enviar {"to":"queued"} produce 400, no 409.

05 · Contrato HTTP

Qué expone la API

El contrato es pequeño intencionalmente. Cubre crear, avanzar, consultar, listar, encontrar el actual y observar salud.

MétodoRutaEntradaResultado
POST/deployments{ service, version } y opcional Idempotency-KeyCrea queued; devuelve 201.
POST/deployments/:id/transitions{ to }Aplica una transición legal; devuelve 200.
GET/deploymentsservice, status, limit, cursor u offsetLista ordenada de más nuevo a más viejo.
GET/services/:name/currentNombre de servicio en la rutaEl succeeded más nuevo; 404 si no existe.
GET/healthNingunastatus, uptime e inFlight.

Validación de entrada

  • JSON mal formado: 400.
  • JSON que no es objeto: 400.
  • Strings vacíos se rechazan.
  • Service y version se recortan con trim().
  • IDs con encoding inválido: 400.
  • Enteros de paginación deben ser seguros.

Mapeo de errores

  • Input inválido: 400.
  • Deployment o current inexistente: 404.
  • Conflicto de negocio o carrera: 409.
  • SQLite ocupada después del timeout: 503.
  • Fallo inesperado: 500.

06 · Decisiones técnicas

Qué se hizo, por qué y para qué

Abre cada decisión para ver el razonamiento. En cada caso también se explica el costo o límite que se aceptó.

1. Bun como runtime, package manager y test runner

Qué: el proyecto declara bun@1.3.14, usa Bun.serve, bun:sqlite y bun:test.

Por qué: mantiene todo el toolchain en el runtime pedido y evita mezclar Node, npm, Vitest o un servidor externo.

Para qué: el mismo entorno instala, ejecuta, prueba y sirve la API. Trade-off: el proyecto queda ligado a APIs de Bun, aunque eso era una restricción explícita y aquí se usa a favor.

2. Bun.serve sin framework HTTP

Qué: server.ts usa directamente Bun.serve, una función handleRequest y expresiones regulares pequeñas para las rutas.

Por qué: hay cinco rutas y ninguna necesita middleware complejo. Un framework agregaría abstracciones y dependencias sin resolver un problema actual.

Para qué: el contrato HTTP queda visible: parsear, validar, llamar al servicio y convertir errores en respuestas. Trade-off: si crece mucho la API, habrá que centralizar routing y middleware.

3. TypeScript estricto y datos externos como unknown

Qué: los contratos usan unions cerradas y propiedades readonly. El parser HTTP y los parsers de SQLite no confían en datos externos.

Por qué: un generic de TypeScript no valida lo que realmente devuelve SQLite ni lo que realmente envía un cliente. El código necesita comprobar tipos en runtime.

Para qué: evitar que un BLOB, status desconocido o timestamp corrupto llegue al dominio como si fuera válido. Trade-off: hay más código de validación, pero el error aparece en el boundary correcto.

4. Separación entre servicio de dominio y repository

Qué: DeploymentService conoce reglas y estados; DeploymentRepository define persistencia; SqliteDeploymentRepository conoce SQL y Bun SQLite.

Por qué: las reglas de negocio no deben depender de SQL concreto ni construir su propia base de datos.

Para qué: probar el dominio con una frontera estable, cambiar la persistencia en el futuro y mantener composición explícita en createApp. Trade-off: hay una interfaz y un objeto adicional para una aplicación pequeña.

5. Estados como union cerrada y tabla explícita de transiciones

Qué: DeploymentStatus solo puede ser queued, running, succeeded, failed o rolled_back. legalTransitions declara las cuatro transiciones válidas.

Por qué: una comparación suelta de strings permitiría olvidar casos. La tabla hace el modelo legible y comprobable.

Para qué: distinguir un target inválido de una transición ilegal y tener un único mapa de la máquina de estados. Trade-off: agregar un nuevo estado exige actualizar tipos, tabla, schema, trigger y pruebas.

6. Normalizar strings antes de consultar o guardar

Qué: service, version, filtros y nombres de servicio pasan por una validación de string no vacío y trim().

Por qué: orders y orders deben representar el mismo servicio; de lo contrario se puede evadir el límite de un deployment activo.

Para qué: hacer consistentes las búsquedas, el índice único, current y las claves de idempotencia. Trade-off: espacios intencionales no se conservan.

7. Idempotencia durable y ligada al payload

Qué: idempotency_keys guarda la clave, service normalizado, version normalizada y deployment ID. Un replay busca el deployment actual en vez de devolver una respuesta inicial congelada.

Por qué: una respuesta puede perderse después de que el servidor ya escribió. El cliente necesita repetir la petición sin duplicar el efecto.

Para qué: reintentos seguros y conflictos explícitos si la misma clave se usa para otro payload. Trade-off: las claves y sus bindings deben conservarse y eventualmente tener una política de retención.

8. Índice único parcial para el deployment activo

Qué: UNIQUE INDEX ... ON deployments(service) WHERE status IN ('queued', 'running').

Por qué: una comprobación en TypeScript sola falla cuando dos procesos consultan “libre” al mismo tiempo. La base de datos debe ser la autoridad atómica.

Para qué: convertir “un activo por servicio” en un invariante que sobrevive a carreras entre conexiones y procesos. Trade-off: el repository debe traducir la constraint a un conflicto de negocio, no a un 500.

9. BEGIN IMMEDIATE para creación

Qué: una transacción inmediata agrupa lookup de idempotencia, chequeo de activo, insert del deployment e insert de la clave.

Por qué: esas cuatro operaciones forman una sola decisión. Si una falla, no debe quedar una mitad escrita.

Para qué: impedir duplicados, claves huérfanas y estados intermedios observables. Trade-off: los writers se serializan y pueden competir por el lock.

10. Transiciones con compare-and-set

Qué: la transacción lee el estado y actualiza con WHERE id = ? AND status = expectedStatus. Después vuelve a leer el registro.

Por qué: dos peticiones pueden leer running; solo una debe ganar el cambio a succeeded o failed.

Para qué: producir una respuesta exitosa y un 409 en la carrera, sin sobrescribir silenciosamente el resultado del otro proceso. Trade-off: el cliente debe reintentar o volver a consultar cuando pierde la carrera.

11. Sequence autoincremental para orden y cursor

Qué: cada fila recibe una sequence INTEGER inmutable. El público sigue viendo un UUID como ID; la sequence se usa internamente para ordenar y crear v1.<base36>.

Por qué: timestamps pueden empatar y UUIDs no expresan orden de inserción. Una sequence del mismo archivo sí ofrece un orden total.

Para qué: newest-first determinista y cursor estable cuando se insertan registros nuevos entre páginas. Trade-off: se valida el límite de enteros seguros de JavaScript.

12. Cursor y offset coexistentes

Qué: cursor filtra sequence < beforeSequence; offset sigue disponible y no se pueden combinar.

Por qué: el cursor permite continuar desde un punto inmutable; offset conserva compatibilidad y es sencillo para clientes que no enfrentan inserciones.

Para qué: ofrecer una opción robusta y otra familiar. Trade-off: offset puede cambiar de contenido si se insertan filas entre dos requests.

13. “Current” significa el succeeded más nuevo

Qué: GET /services/:name/current selecciona el succeeded con mayor sequence, no un campo mutable de “current”.

Por qué: evita mantener una segunda fuente de verdad y hace que el rollback sea una operación histórica, no una reescritura.

Para qué: si el último succeeded se marca rolled_back, el succeeded anterior emerge automáticamente. Trade-off: current requiere una consulta ordenada.

14. SQLite nativo en vez de memoria o ORM

Qué: bun:sqlite guarda datos en un archivo configurable por DATABASE_PATH; los tests usan bases temporales o in-memory.

Por qué: la memoria se pierde al reiniciar y el ejercicio pedía persistencia. Un ORM sería una capa extra para un schema pequeño donde se necesitan índices, triggers y PRAGMAs explícitos.

Para qué: persistencia local, coordinación entre procesos del mismo host y control directo de constraints. Trade-off: SQLite no es una base distribuida y los writers compiten por un lock.

15. Foreign keys, WAL y busy timeout

Qué: cada conexión activa foreign keys; los archivos usan WAL; el timeout por defecto es 1 segundo y es configurable entre 0 y 60.000 ms.

Por qué: foreign keys protegen relaciones, WAL permite que lectores y writers interfieran menos, y busy timeout da una ventana para locks breves.

Para qué: hacer predecible la operación en un archivo compartido y traducir contención agotada a 503. Trade-off: WAL no convierte SQLite en multi-host; además hay que respaldar los sidecars y probar restauración.

16. Migrations versionadas y validación semántica

Qué: PRAGMA user_version lleva el schema de 0 a 3: tablas e índices, triggers y luego reparación/fortalecimiento del schema.

Por qué: “la tabla existe” no demuestra que tenga el índice, predicate, trigger o foreign key correctos. El startup inspecciona columnas, SQL, índices, triggers, foreign keys y range de sequence.

Para qué: fallar temprano ante una base futura o counterfeit/corrupta en vez de aceptar invariantes falsas. Trade-off: cada cambio de schema necesita código de migración y fixtures de prueba.

17. Parsers de filas SQLite

Qué: los resultados de consultas se leen como unknown y se validan en sqlite-row-parsers.ts.

Por qué: el tipo genérico de una query describe la expectativa del programador, pero no garantiza el contenido de una base dañada o manipulada.

Para qué: rechazar status no conocidos, strings vacíos, timestamps no canónicos, BLOBs donde debía haber texto y sequences fuera de rango. Trade-off: la capa de storage es más verbosa.

18. Errores de SQLite separados de errores de API

Qué: el repository clasifica busy/locked como StorageBusyError y constraints como StorageConstraintError; el servicio las convierte a respuestas adecuadas.

Por qué: el dominio no debería depender de SQLiteError, pero tampoco debe perder la diferencia entre un conflicto esperado y una falla interna.

Para qué: devolver 503 para reintento, 409 para active-service y 500 para corruption/unclassified. Trade-off: el mapping debe mantenerse preciso para no ocultar bugs como conflictos de negocio.

19. Ownership y shutdown del servidor

Qué: si createApp crea el service, también cierra SQLite al detenerse; si recibe un service inyectado, no lo cierra. server.stop es idempotente y el bind fallido también limpia el recurso propio.

Por qué: los recursos deben tener un dueño claro. Cerrar un service inyectado rompería al caller; no cerrar uno creado internamente deja handles abiertos.

Para qué: evitar leaks en tests, reinicios y errores de startup sin cambiar el contrato nativo de Bun.Server. Trade-off: envolver stop requiere tests de lifecycle.

20. CI con instalación congelada

Qué: el workflow usa acciones fijadas por SHA, Bun 1.3.14, bun install --frozen-lockfile, typecheck, lint y bun test en push y pull request.

Por qué: no basta con que funcione en la laptop; el lockfile y la versión del runtime deben ser reproducibles en CI.

Para qué: detectar regresiones antes de publicar. Importante: el workflow actual valida; no implementa un deploy SSH. La explicación de producción separa CI de la estrategia de despliegue.

07 · Persistencia

Qué guarda SQLite

La base tiene dos tablas principales. La información durable permite reconstruir el estado después de cerrar y volver a abrir el proceso.

deployments

Historia de deployments

  • sequence: orden interno autoincremental.
  • id: UUID público único.
  • service y version: payload normalizado.

  • request_key: clave primaria.
  • deployment_id: foreign key a deployments.

09 · Honestidad técnica

Qué no está resuelto por este proyecto

Una buena explicación también debe marcar los límites. Estas no son fallas frente al alcance actual; son decisiones de alcance o siguientes pasos para producción real.

No incluido

Autenticación y autorización

La API no verifica quién puede crear, avanzar o rollbackear un deployment. En producción debe quedar detrás de un gateway, identity provider o middleware de autorización.

No incluido

Executor de despliegues

El proyecto registra y coordina estados, pero no ejecuta SSH, Docker, Kubernetes ni una plataforma cloud. Un worker externo tendría que traducir queued a una acción real.

Límite

SQLite es de un host

WAL y varios procesos ayudan dentro del mismo host. No se debe poner el archivo en un filesystem de red ni escalar varios hosts con SQLite como writer. Para eso, PostgreSQL.

Hardening

Controles operativos

Body-size limits, rate limiting, retención de idempotency keys, métricas, backups off-host y alertas deben agregarse según el entorno operativo.

Cómo responderlo en entrevista: “El ejercicio pedía el API y sus invariantes, no una plataforma completa de deployment. Por eso separé el control plane de la ejecución. En producción agregaría autenticación, un executor, backups y observabilidad; si necesito varios hosts, migraría el repository a PostgreSQL.”

10 · Preparación

Preguntas que puede hacer un reclutador técnico

Las respuestas están escritas para explicar el razonamiento, no para memorizar frases. Empieza por el problema, luego el mecanismo y finalmente el trade-off.

¿Cuál es el problema que resuelve?
Coordina el ciclo de vida de despliegues de servicios y conserva una fuente durable de verdad. Evita dos deployments activos para el mismo servicio, hace seguros los reintentos, impide transiciones inválidas y permite consultar el deployment actual y el historial.
¿Esto despliega realmente una aplicación?
No por sí solo. Es la API de coordinación y registro. Puede ser llamada por un CI pipeline, un worker o un sistema interno que sí ejecute la infraestructura. Mantener esa frontera evita fingir que una API de estado ya es un executor de Docker, SSH o Kubernetes.
¿Por qué SQLite y no PostgreSQL?
El alcance pide persistencia local y el servicio puede correr en un host. SQLite evita una dependencia externa y permite usar constraints y transacciones reales. PostgreSQL sería la siguiente opción si hubiera varios hosts, failover o escritura sostenida alta.
¿Cómo impides dos deployments activos?
El servicio hace un chequeo para dar un error claro, pero la garantía real está en un partial unique index sobre service filtrado a queued y running. Si dos procesos llegan juntos, SQLite decide atómicamente cuál insert gana.
¿Por qué no basta con un Map en memoria?
Un Map desaparece al reiniciar, no coordina procesos separados y no ofrece constraints persistentes. SQLite conserva el historial, el binding de idempotencia y la regla de un activo entre conexiones del mismo archivo.
¿Qué significa idempotency en este proyecto?
Una misma clave y el mismo service/version representan una sola operación lógica. El replay devuelve el mismo deployment ID en su estado actual. La clave no puede reutilizarse con un payload diferente, porque eso sería mezclar dos operaciones.
¿Por qué la transacción es BEGIN IMMEDIATE?
La creación tiene varias operaciones que deben ser una sola unidad: lookup de clave, chequeo de activo, insert de deployment e insert de binding. IMMEDIATE toma temprano la reserva de escritura y evita que dos writers atraviesen el mismo chequeo como si fueran únicos.
¿Cómo resuelves dos transitions simultáneas?
La query actualiza solo si el status sigue siendo el que se leyó: WHERE id = ? AND status = expectedStatus. Una request cambia primero; la otra ve cero filas afectadas y recibe 409.
¿Por qué no ordenar por timestamp?
Dos inserts pueden tener el mismo millisecond timestamp. La sequence autoincremental entrega un orden total dentro de la base. El UUID se conserva como identificador público, pero no se usa para ordenar.
¿Cuál es la diferencia entre cursor y offset?
Offset salta una cantidad de filas y se mantiene por compatibilidad, pero nuevas inserciones pueden mover las páginas. Cursor guarda una sequence anterior y pide filas menores a ella, por lo que es la opción recomendada para recorrer mientras llegan nuevos deployments.
¿Cómo defines “current”?
No existe un booleano current que pueda quedar desactualizado. Current es el deployment más nuevo que sigue en succeeded. Si el último succeeded pasa a rolled_back, el anterior succeeded vuelve a aparecer como current.
¿Por qué rollback no borra el deployment?
Borrar historia destruye auditoría y dificulta entender qué ocurrió. rolled_back es un estado terminal histórico; la consulta current simplemente ignora esa fila y encuentra el succeeded anterior.
¿Qué protegen los triggers si el servicio ya valida?
Protegen contra escrituras que lleguen desde otra conexión o herramienta y evadan DeploymentService. El servicio da errores de negocio claros; SQLite mantiene la invariante aunque el caller cambie.
¿Qué pasa si la base está corrupta?
El startup valida schema, columnas, constraints, índices, triggers, foreign keys y sequence. Las filas leídas se validan como datos no confiables. Un esquema o fila inválidos fallan explícitamente en vez de transformarse silenciosamente en un deployment válido.
¿Por qué validar SQLite si TypeScript ya tiene tipos?
TypeScript desaparece en runtime. Además, la base puede haber sido editada, estar dañada o devolver un valor con un tipo inesperado. Por eso las queries se reciben como unknown y los parsers validan el contenido real.
¿Qué hace WAL y qué no hace?
WAL permite que lectores y writers interfieran menos en un archivo local y mejora la convivencia entre procesos. No convierte SQLite en una base multi-host ni elimina la serialización de writers.
¿Por qué un lock termina en 503?
Una contención de SQLite agotada normalmente es temporal. 503 le dice al cliente que el servicio está temporalmente no disponible y que puede reintentar. Devolver un 500 perdería información operativa; devolver 409 lo confundiría con un conflicto de negocio.
¿Por qué hay un repository interface?
Aísla las reglas de negocio de la tecnología de almacenamiento. Permite probar el servicio con otra implementación y hace posible reemplazar SQLite por PostgreSQL sin reescribir las rutas y la máquina de estados.
¿Por qué no agregaste un ORM?
El schema es pequeño y requiere SQL específico: partial index, triggers, PRAGMAs, migrations y queries ordenadas por sequence. Un ORM agregaría una capa de traducción sin una necesidad concreta. El SQL explícito hace visibles las invariantes.
¿Cómo se probó la concurrencia real?
Además de requests concurrentes en el mismo servidor, hay fixtures que arrancan procesos Bun separados contra el mismo archivo SQLite. Se prueban races de active-service, idempotencia con la misma clave, payloads en conflicto y transitions competitivas.
¿Qué demuestra CI?
El workflow fija Bun 1.3.14, instala con el lockfile congelado, ejecuta typecheck, lint y todos los tests en cada push y pull request. CI valida el código; no implementa automáticamente un deploy SSH al VPS.
¿Qué harías antes de producción?
Añadiría autenticación/autorización, límite de body y tamaños de input, backup off-host con restore probado, métricas y alertas. Usaría Caddy y systemd en un VPS, mantendría SQLite en disco local y migraría a PostgreSQL antes de ejecutar varias réplicas en hosts distintos.
¿Cuál es el principal límite del diseño?
SQLite coordina muy bien un host, pero no es la elección para una topología distribuida. El límite está documentado explícitamente: cuando la necesidad pasa a ser multi-host o write-heavy, se conserva el contrato del repository y se cambia el backend a PostgreSQL.
¿Por qué no incluiste autenticación?
Porque el alcance del ejercicio se concentra en lifecycle, persistencia, API y concurrencia. No significa que una API pública de producción deba estar abierta. La autenticación debe estar en el gateway o en una capa de seguridad añadida antes de exponerla.
¿Qué diferencia hay entre 400, 404, 409 y 503?
400 significa que la petición no es válida; 404, que el recurso no existe; 409, que la petición válida entra en conflicto con el estado actual; 503, que SQLite no pudo completar por contención temporal. La distinción ayuda al cliente a decidir si corregir, consultar, no reintentar o reintentar.
¿Qué cambiarías si el proyecto creciera?
Mantendría la máquina de estados y el contrato del service, reemplazaría SQLite por PostgreSQL, añadiría un executor durable con una cola o scheduler, autenticación, observabilidad y una estrategia de deploy real. El límite está localizado gracias a la frontera del repository.
